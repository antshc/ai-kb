= How Claude Agent Coding Saves Progress Between Retries
:toc:
:toclevels: 3
:sectnums:

In *Claude-style agent coding*, “saving progress between retries” is basically *externalizing the agent’s brain* so a retry does *not* start from zero.

== Short answer

When an agent fails, times out, gets compacted, or is retried, it can continue *only if the important state was written somewhere outside the model context*, such as:

* task files (`TASKS.md`)
* progress / learnings files (`PROGRESS.md`)
* project memory (`CLAUDE.md`)
* result files per subtask (`.claude/results/*.md`)
* sometimes hook-based summaries before compaction or session end

That is the core trick:

*LLM memory is temporary, files are durable.*

== The real problem retries are solving

An agent can “lose its mind” for a few reasons:

. Tool error / command failure
. Context window gets compressed
. Subagent crashes or stops halfway
. You restart the session
. You tell it “retry” after a bad attempt

If the agent kept all its understanding only in the conversation, then on retry it has to:

* re-read files
* re-discover architecture
* re-figure out what failed
* often repeat the same mistake

That is expensive and dumb.

So the better pattern is:

[quote]
____
After every meaningful step, persist state to disk.
On retry, restore from disk first.
____

== Mental model: Agent = CPU, Files = RAM/SSD

Think of it like this:

* *Claude context window* = CPU registers / cache → very fast, but tiny and volatile
* *Files in repo* = RAM / disk → slower, but persistent
* *Retry* = process restart

So if you want retries to be reliable, you must store:

* what was the plan
* what is already done
* what failed
* what remains
* what rules/patterns were learned

== The retry-safe workflow

Here’s the clean pattern.

=== 1) Before doing work → read state

At the beginning of each attempt, the agent should read:

* `CLAUDE.md` → permanent project rules / architecture
* `TASKS.md` → task list and statuses
* `PROGRESS.md` → recent learnings and current state
* `.claude/results/*.md` → outputs of completed subagents

This gives the agent a *cold-start recovery point*.

==== Example

[source,md]
----
# TASKS.md

| ID     | Task                                | Status      |
|--------|-------------------------------------|-------------|
| ST-001 | Add journal cache disk abstraction  | DONE        |
| ST-002 | Implement cache capacity check      | IN PROGRESS |
| ST-003 | Add tests for disk full fallback    | TODO        |
----

On retry, Claude reads this and immediately knows:

* ST-001 is done
* ST-002 is partially done
* ST-003 not started

No need to guess.

=== 2) During work → checkpoint progress

The most important thing is to *checkpoint after each meaningful milestone*, not only at the end.

That means after:

* a file edit batch
* a design decision
* a failed experiment
* a test run
* a subtask completion

write a small structured update.

==== Example checkpoint

[source,md]
----
# PROGRESS.md

## Current Focus
ST-002 - Implement cache capacity check

## Done
- Added DiskSpaceMonitor abstraction
- Wired monitor into JournalCacheWriter

## Failed Attempts
- Tried checking free space on every write -> too expensive
- Decided to use periodic refresh instead

## Next Step
- Disable cache when free disk space is below threshold
- Re-enable when space recovers

## Risks
- Race conditions between check and actual write
----

Now if the agent crashes, the retry starts from here instead of from “what were we doing again?”

== The key retry principle: Save decision state, not just code

Most people save only code changes.

That’s not enough.

The *valuable thing* to save is:

* *why* the agent chose a direction
* *what failed*
* *what not to retry*
* *what assumption is currently true*

Because on retries, the biggest waste is not “rewriting code” — it’s *repeating bad reasoning*.

=== Bad persistence

[source,md]
----
Implemented cache monitor.
----

This is useless.

=== Good persistence

[source,md]
----
Implemented cache monitor using periodic disk checks every 30s.
Rejected per-write free space checks because they add overhead to every IO path.
If disk is full, cache must be disabled and reads should fall back to journal directly.
----

Now the retry does not re-argue the same design from scratch.

== How retries work with subagents

This is where the pattern becomes really important.

If Claude launches subagents (or “Task” style workers), each subagent should:

. do exactly *one atomic task*
. write its output to a *result file*
. return only a tiny summary

That way, if the parent retries, it does *not* need the full subagent transcript.

=== Good subagent pattern

==== Parent task list

[source,md]
----
| ID     | Task                                | Status |
|--------|-------------------------------------|--------|
| ST-101 | Add disk space abstraction          | DONE   |
| ST-102 | Implement cache disable behavior    | DONE   |
| ST-103 | Add tests                           | TODO   |
----

==== Subagent result file

[source,md]
----
# .claude/results/ST-102.md

Status: DONE

Files:
- JournalCacheWriter.cs
- DiskSpaceMonitor.cs

Learned:
- Cache writes must short-circuit when disk threshold is exceeded.
- Fallback path already exists and can be reused.

Notes:
- Do not throw when cache is full; degrade gracefully.
----

Now if the orchestrator is retried:

* it just re-reads `ST-102.md`
* marks task as done
* moves on

It does *not* need the full conversation that produced that result.

== What “save progress between retries” actually means in practice

It usually means saving *five layers of state*.

=== Layer 1 — Task state

What work exists and its status.

Example:

[source,text]
----
TODO / IN PROGRESS / DONE / BLOCKED
----

This prevents duplicate work.

=== Layer 2 — Execution state

What the agent was doing right before failure.

Example:

[source,text]
----
Currently implementing:
- threshold-based disable logic

Last completed:
- periodic disk polling

Next command to run:
- dotnet test --filter "JournalCache"
----

This prevents “where was I?” confusion.

=== Layer 3 — Decision state

What architectural choices were made.

Example:

[source,text]
----
Use periodic disk checks, not per-write checks.
Use graceful fallback, not exceptions, when cache is full.
----

This prevents retry loops.

=== Layer 4 — Artifact state

What outputs already exist.

Example:

* created files
* modified files
* generated test data
* partial implementation

This prevents redoing completed work.

=== Layer 5 — Failure state

What already failed and why.

Example:

[source,text]
----
Attempted direct DriveInfo("/") call in Linux container test environment.
Failed because test sandbox permissions differ.
Need abstraction + mocking.
----

This is gold.

Without this, retries often become *doom loops*.

== Why retries fail without saved progress

Because the model tends to do this:

. sees failure
. guesses the cause
. retries with slightly different guess
. fails again
. keeps spiraling

That is the classic *agent doom loop*.

=== Example doom loop

Problem: tests fail due to permission issue.

Bad retry behavior:

* Retry 1: change file permissions
* Retry 2: add `sudo`
* Retry 3: write to another temp folder
* Retry 4: disable test
* Retry 5: change unrelated code

Why? Because the agent never persisted:

[quote]
____
“Root cause is test environment ownership mismatch, not app logic.”
____

So the fix is to save this:

[source,md]
----
Root cause identified:
Permission failure comes from environment setup, not journal cache logic.

Do not retry:
- chmod/chown inside app code
- changing cache logic

Next correct action:
- isolate test temp path ownership
----

That one note can save 5 useless retries.

== Best practice: make retries idempotent

This is the engineering part.

A good agent step should be safe to rerun.

=== Good retry-safe step

[source,text]
----
If result file exists and says DONE -> skip
If migration already applied -> skip
If code already inserted -> do not duplicate
If tests already green -> move to next step
----

This is exactly how reliable CI/CD pipelines work too.

=== Bad retry-unsafe step

[source,text]
----
Append same config block again
Recreate same files blindly
Re-run destructive rename
Re-add same dependency
----

That creates messy repeated changes.

So a good Claude agent should behave like this:

[quote]
____
Before doing work, first check whether the work is already done.
____

That’s the difference between a workflow engine and a chaotic autocomplete goblin.

== The ideal retry loop

Here is the clean sequence.

=== Retry-safe Claude agent loop

. *Restore*
+
Read:
* `CLAUDE.md`
* `TASKS.md`
* `PROGRESS.md`
* recent result files

. *Reconcile*
+
Ask:
* What is already done?
* What was the last unfinished task?
* Was there a known blocker?

. *Resume*
+
Continue only the *next incomplete atomic task*.

. *Verify*
+
Run:
* build
* tests
* lint
* smoke check

. *Checkpoint*
+
Update:
* task status
* learnings
* blockers
* next step

. *Only then continue*

That is how you survive retries cleanly.

== Best file structure for Claude agent coding

Here’s a simple version that works well.

[source,text]
----
/project-root
  CLAUDE.md
  TASKS.md
  PROGRESS.md
  .claude/
    results/
      ST-001.md
      ST-002.md
    handoff.md
    failures.md
----

=== What each file does

==== `CLAUDE.md`

Permanent rules:

* architecture
* coding conventions
* project invariants
* “always do X, never do Y”

==== `TASKS.md`

Execution backlog:

* TODO / DONE / BLOCKED

==== `PROGRESS.md`

Short-term working memory:

* current focus
* recent decisions
* next step

==== `.claude/results/*.md`

Per-task outputs:

* what changed
* what was learned
* result status

==== `.claude/handoff.md`

Session restart / retry summary:

* “what next Claude should do first”

==== `.claude/failures.md`

Mistake log:

* failed approaches
* root causes
* anti-patterns to avoid

== The most important insight

Claude does *not* “remember between retries” by magic.

It only appears to remember if you gave it a *reconstruction mechanism*.

That reconstruction mechanism is usually:

* *structured files*
* *hooks*
* *checkpoints*
* *small atomic tasks*

So the real answer is:

[quote]
____
Claude saves progress between retries only if the workflow is designed to persist progress outside the conversation.
____

That’s the whole game.

== Best practical rule for you

Since you’re doing engineering work, the most useful pattern is this:

=== For every task, always persist:

* *What I changed*
* *What failed*
* *Why I chose this approach*
* *What should happen next*

If you do only that, your retries become *10x more stable*.

== Ultra-short version to remember

=== Claude retry memory formula

*Retry-safe agent =*
*small tasks*
+ *checkpoint files*
+ *decision log*
+ *failure log*
+ *idempotent reruns*

Or even shorter:

[quote]
____
Don’t trust the model to remember.
Teach it to leave notes for its future self.
____
