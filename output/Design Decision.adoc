= Compact OpenSpec Design Decisions (Copilot-Friendly)
:toc:
:toclevels: 2

== Goal of the Design Section

Design is *not* full implementation.
Design is *clear decisions mapped to code structure*.

It should answer:

* What are we building?
* Where in the code?
* How components interact?
* Why this approach (briefly)?

---

== Compact Design Decision Format (Recommended)

Use one block per decision, minimal but structured:

## [source,adoc]

== Decision: <short name>

=== Context
<1–2 lines problem or constraint>

=== Change

* Class: `<ClassName>`
* Methods:

  * `<MethodA>(...)` -> <purpose>
  * `<MethodB>(...)` -> <purpose>
* Dependencies:

  * `<InterfaceA>` used for <reason>

=== Flow
<1–3 bullets or simple steps>

=== Alternatives (optional)

* `<Option>` -> rejected because <reason>

---

---

== Example (Minimal, Realistic)

## [source,adoc]

== Decision: Add order creation orchestration

=== Context
Order creation requires validation + payment + persistence.

=== Change

* Class: `OrderService`
* Methods:

  * `CreateOrderAsync(request)` -> orchestrates flow
* Dependencies:

  * `IPaymentService` -> process payment
  * `IOrderRepository` -> save order

=== Flow

1. Validate request
2. Call `IPaymentService`
3. Save via `IOrderRepository`

=== Alternatives

* Controller orchestration -> rejected (breaks separation of concerns)

---

---

== Level of Detail (What is “Just Right”)

Think in three levels:

=== Too Low (Bad)

## [source,adoc]

## Use service to handle orders

Problem:

* No classes
* No methods
* Cannot map to code

---

=== Too Detailed (Also Bad)

## [source,adoc]

## Use try/catch, logging, async/await, null checks...

Problem:

* Implementation noise
* Reduces clarity

---

=== Just Right (Target)

## [source,adoc]

* Class: `OrderService`
* Method: `CreateOrderAsync`
* Uses: `IPaymentService`, `IOrderRepository`
* Flow: validate -> pay -> save

---

Why:

* Maps directly to code
* Leaves freedom for implementation
* Enables task generation

---

== What MUST Be Included (High Value)

Always include:

* Class names → anchor to codebase
* Method names → enable code generation
* Dependencies (interfaces) → define boundaries
* Flow (short) → describe orchestration

---

== What to Avoid

Do NOT include:

* Low-level code (loops, try/catch, logging)
* Framework noise (DI config, attributes unless critical)
* Generic statements ("ensure scalability", "handle errors")
* Long paragraphs

---

== Ultra-Compact Variant

For maximum brevity:

## [source,adoc]

== Decision: Order creation

* Class: `OrderService`
* Method: `CreateOrderAsync`
* Uses: `IPaymentService`, `IOrderRepository`
* Flow: validate -> pay -> save

---

Best for:

* Large designs
* Fast iteration
* AI-assisted workflows

---

== Why This Works

* Class + method names = direct mapping to code
* Each method becomes a natural task
* Easy to scan in reviews
* Shows architecture without over-explaining

---

== Rule of Thumb

If a developer can implement the feature without asking
"Where should this go?", the design detail is correct.
